# UNIPLEX — главный паспорт проекта

Последнее обновление: 27 ноября 2026 года

## 1. Назначение проекта

UNIPLEX — модульная AI-система для автоматизации управления производственным бизнесом по выпуску подложки под ламинат.

Цель — создать единую систему, которая собирает информацию из деловой переписки и документов, структурирует её, хранит историю и предоставляет AI-агентам достоверный контекст для ответов и дальнейшей автоматизации процессов.

## 2. Основные принципы

- PostgreSQL — основной источник достоверных структурированных данных.
- Qdrant — векторная база для семантического поиска.
- RAG — слой поиска и предоставления контекста AI-моделям.
- Точные остатки, суммы, количества и финансовые показатели получать из PostgreSQL, а не вычислять по результатам семантического поиска.
- Сохранять происхождение каждого факта: письмо, вложение, документ, дата, версия и место в источнике.
- Сохранять историю изменений, не затирать важные предыдущие значения.
- Автоматизировать обработку, но контролировать неоднозначные и конфликтующие сведения.
- Использовать внешние AI API; локальные большие модели на текущем VPS не планируются.
- Не отправлять письма от имени системы без отдельного согласования архитектуры и разрешений.

## 5. Почтовый модуль

Используется отдельный почтовый ящик Яндекса, доступный системе по IMAP только для чтения.

Основной Mail.ru ящик напрямую к серверу не подключается. Копии писем пересылаются в отдельный ящик.

Реализовано:
- импорт заголовков писем;
- синхронизация INBOX;
- получение тела письма через BODY.PEEK;
- MIME-разбор;
- извлечение вложений;
- обработка кириллических имён файлов;
- контроль размеров и хешей;
- сохранение метаданных в PostgreSQL.

Почтовый импортёр и обработчик писем разделены.

Ориентировочное количество писем при последней проверке: 1027.

## 9. Политика достоверности данных

Каждый извлечённый факт должен иметь:
- значение;
- тип и ключ поля;
- источник;
- дату и контекст;
- уверенность;
- версию извлечения;
- статус обработки.

Неоднозначные данные и конфликты нельзя автоматически использовать для перезаписи достоверных бизнес-фактов.

Целевая модель автоматизации:
- однозначные факты с высокой уверенностью могут приниматься автоматически по установленным правилам;
- сомнительные факты направляются на проверку;
- конфликты сохраняются и выявляются отдельно;
- история исходных значений не теряется.

## 12. Правила работы с сервером

- Не запрашивать у пользователя пароли, приватные ключи и API-токены.
- Не помещать секреты в GitHub.
- Не подключать основной Mail.ru ящик напрямую.
- Не отправлять письма из системы.
- Не удалять рабочие данные и резервные копии без проверки и явного согласования.
- Не запускать платные AI-запросы без разрешения.
- Не использовать `docker compose down -v` и не удалять контейнеры через `--remove-orphans` без отдельной проверки.
- Не менять схему БД без проверки миграций и резервной копии.
- Команды на сервере выполнять по одной, проверяя результат каждой.
- Не считать команду выполненной, пока пользователь не показал её результат.
